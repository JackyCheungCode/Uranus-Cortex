# 前端工程与模块化规范

- 状态：强制工程规范
- 适用范围：Uranus-Cortex 全部前端页面、组件、样式、测试与文档
- 优先级：遵循仓库根目录 `AGENTS.md`；Carbon 组件行为以 IBM 官方文档为准

## 1. 不可违反的原则

1. **模块化**：按业务领域组织代码，明确模块职责、依赖方向和公开接口。
2. **Carbon-first**：所有产品 UI 遵循 IBM Carbon Design System。先查找 Carbon 官方组件和模式，再考虑定制。
3. **Frontend-first**：第一阶段只设计和实现前端体验。默认使用类型化 Mock 数据与 Mock Service，不连接真实数据库、认证、外部业务 API 或生产服务。
4. **类型安全**：启用 TypeScript strict 模式；避免 `any`、隐式类型和未经验证的数据形状。
5. **可访问与响应式**：目标 WCAG 2.2 AA；交互支持键盘、可见焦点、语义标签和合理的窄屏体验。
6. **可验证**：交付必须报告实际运行的类型检查、Lint、测试和构建结果；未运行的检查必须明确说明。

## 2. 技术基线

- React + TypeScript + Vite。
- UI：`@carbon/react`、`@carbon/styles` 及 Carbon 官方图标包；版本须由项目依赖统一锁定。
- 布局优先使用 Carbon Grid 和官方布局模式。
- 样式优先使用 Carbon 主题、设计令牌和 Sass；不得在各模块建立互相竞争的 token 系统。
- 路由按业务模块组织；采用项目现有路由方案，新增路由依赖需说明理由。
- 测试沿用项目现有 Vitest / Testing Library 配置；不随意引入重复测试框架。

## 3. 模块化与依赖边界

建议的目录基线如下。可按项目实际规模增减目录，但不得改变职责边界来规避规范。

```text
src/
├── app/                 # 应用入口、路由、全局 Provider
├── shell/               # 应用框架：Header、导航、页面布局
├── modules/             # 业务领域模块
│   ├── dashboard/
│   ├── discovery/
│   ├── buyers/
│   ├── crm/
│   ├── integrations/
│   └── settings/
├── components/          # 跨业务模块复用的领域无关组件
├── design-system/       # 经审查的项目级 Carbon 组合与设计令牌
├── services/            # 全局服务接口与 Mock 实现
├── hooks/               # 跨模块通用 Hooks
├── types/               # 真正跨模块共享的类型
├── utils/               # 纯通用工具
└── styles/              # 全局样式入口
```

业务模块按需要使用以下内部结构：

```text
modules/<module>/
├── pages/
├── components/
├── hooks/
├── services/
├── types/
├── utils/
├── __tests__/
└── index.ts             # 模块公开接口
```

### 依赖规则

- 页面负责布局和编排；业务规则放在模块 Hooks、服务或纯函数中，不把所有逻辑塞进 JSX。
- 模块内部组件默认不对其他模块开放。跨模块调用通过该模块的 `index.ts` 公开接口。
- 禁止导入其他模块的内部路径，例如 `modules/buyers/components/...`；应从其公开入口导入。
- 共享组件必须是实际存在跨模块复用需求的通用能力；不要提前建设过度抽象的组件平台。
- 共享类型只放入全局 `types/`；领域专属类型保留在所属模块。
- 避免循环依赖；模块依赖方向必须能被解释并通过代码审查。
- 单个组件、Hook 或服务保持单一明确职责；是否拆分以可读性、测试性和复用需求为准，而不是追求文件数量。

## 4. Carbon 设计和实现规则

- 优先使用 `@carbon/react` 中已有的组件和官方推荐模式；不重新实现按钮、输入、弹窗、通知、表格、下拉框、焦点管理或键盘行为。
- 使用 Carbon 主题和 token 处理颜色、间距、排版、边框、层级和动效。存在对应 token 时，禁止任意硬编码数值。
- 使用 Carbon Icons；不得用 Emoji 或未经批准的图标包充当产品功能图标。
- 不得引入另一套重叠的 UI 组件库或自行建立平行设计系统。
- 自定义组件应优先组合 Carbon 组件。确实无法满足需求时，记录原因、交互和无障碍影响、测试证据，并按 `docs/design/carbon-standards.md` 走例外审查。
- 页面视觉质量通过信息层级、留白、对齐、可读性、操作一致性和适当的信息密度实现；避免无目的的渐变、装饰性阴影、重复卡片和不一致的圆角。
- 页面应明确主标题、说明、主要操作、内容区域及反馈信息。复杂数据页面需设计筛选、排序、空状态和窄屏使用方式。
- 所有有状态交互应覆盖适用的加载、空、成功、验证错误、失败、禁用和权限状态；不能只做静态截图式页面。
- 保留语义 HTML、合理标题层级、可访问名称、键盘操作、可见焦点、错误关联和 reduced-motion 支持；状态不能只靠颜色传达。

## 5. 前端优先阶段的范围

### 允许

- 页面与导航设计、交互原型、响应式布局。
- Carbon 组件组合、类型定义、Mock fixtures、Mock Service。
- 查询构建器、筛选、分页、模拟进度、结果预览、详情和表单状态。
- 单元/组件测试、可访问性检查和视觉验收。
- 为未来服务集成定义稳定的 TypeScript 接口和错误类型。

### 未经明确授权禁止

- 连接或修改 Supabase、真实数据库、认证提供商或生产数据。
- 调用真实搜索、AI、抓取或其他外部业务 API。
- 保存真实 API Key、Token、密码或个人数据。
- 修改 Cloudflare 生产配置、部署应用或更改生产资源。
- 将模拟的成功状态描述成真实服务已连通、真实数据已保存或真实搜索已完成。

### Mock 与真实服务隔离

- UI 通过服务接口取数，不直接导入 Mock 数据文件。
- Mock 与未来真实实现遵循相同的输入、输出和错误类型。
- 通过依赖注入或明确的服务装配点切换实现，不在页面中散布环境判断。
- Mock 数据须清晰标注为示例数据；模拟延迟和失败只用于验证交互，不得冒充真实结果。
- 不在浏览器、Local Storage 或前端构建产物中放置任何服务端密钥。

## 6. 视觉和交互验收

每个页面至少检查：

1. Carbon 组件、主题和 token 使用正确，视觉语言与全站一致。
2. 信息层级清楚，主要任务和主要操作易于发现。
3. 所有可见操作可用，交互结果明确，无空壳按钮。
4. 适用的加载、空、错误、成功、禁用状态完整。
5. 桌面、平板、窄屏及缩放重排合理；无横向溢出或内容遮挡。
6. 键盘顺序、焦点状态、标签、错误提示和语义结构可用。
7. 组件逻辑可测试，模块之间没有未声明的内部依赖。
8. 没有未经批准的颜色、间距、字体、图标或 CSS 覆盖。
9. 类型检查、Lint、测试和生产构建结果已记录。
10. 未实现的后端能力明确标注为 Mock 或“尚未接入”。

## 7. 变更流程

1. 开发前阅读 `AGENTS.md`、本文件、Carbon 标准、架构文档和相关产品需求。
2. 先列出页面状态、用户操作、Carbon 组件选择、模块归属和 Mock 接口。
3. 先实现最小可演示的前端切片；避免无关重构和一次性铺开全部业务。
4. 为行为与关键状态添加测试，并执行项目可用的质量检查。
5. 提交时说明改动范围、设计选择、检查命令及结果、未完成项和 Mock 边界。
6. 任何规范例外均需书面记录和人工审查；工具通过不等于例外获批。
